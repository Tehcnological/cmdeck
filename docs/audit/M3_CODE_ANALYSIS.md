## 5. Plugin-host evaluation (M3-37)

**What it is.** A filesystem plugin directory (`<baseDir>/plugins/*/plugin.json`; standalone
default `~/.m3`), validated manifests (`m3:m3/plugin-host/manifest.ts` `validatePluginManifest`),
two runtimes — `static` (HTML served from `/api/m3-plugins/static/<id>/…`) and `sidecar` (spawned
command on a random loopback port, proxied at `/api/m3-plugins/sidecar/<id>/…`,
`PluginHostManager.ensureSidecarRunning`) — four UI slots (`sidebar-tab`, `right-panel`,
`thread-toolbar`, `modal`) rendered as iframes by `apps/web/src/components/M3PluginSlotHost.tsx`,
and a versioned `postMessage` bridge (`bridgeProtocol.ts`). Install from git URL, local copy or
symlink; enable/disable/reload. Server glue is one route layer (`apps/server/src/m3PluginRoute.ts`).
Tests: 3 unit cases (`PluginHostManager.test.ts`) + 1 route-auth case (`m3PluginRoute.test.ts`). No docs.

**Findings (source-level).**

- **No real isolation in the browser.** Every iframe uses `sandbox="allow-scripts allow-forms
  allow-same-origin"` (`M3PluginSlotHost.tsx:339,396,442,500`) on content served from the app's
  own origin. That combination lets plugin script reach `window.parent`, the app's storage and
  authenticated requests — the sandbox is ineffective. No CSP is set on plugin responses
  (`httpHandler.ts`).
- **No isolation on the host.** Sidecars inherit the full server `process.env`
  (`PluginHostManager.ts`, `env: { ...process.env, ...manifest.runtime.env, … }`) and run
  unsandboxed with the server user's rights. `install` clones any git URL.
- **Auth was missing until the day of the audit**: `/api/m3-plugins/*` was unauthenticated
  (remote code execution via `POST /install`) until `ab16580c1` (#33) required
  `environment:maintain`.
- **Bridge is mostly stubs.** `thread:create`, `prompt:inject` and `file:open` dispatch
  `m3-plugin:*` window events that nothing listens to (grep: no listener in `apps/` or
  `packages/`). The server publishes only `plugins:reloaded`; none of the declared events
  (`thread:updated`, `agent:spawned`, …) is wired to orchestration.
- **Not multi-surface / remote-ready.** `API_BASE = "/api/m3-plugins"` is page-relative, so it
  only reaches the environment that served the web bundle (not other environments, not
  app.t3.codes); no mobile host; not exposed as MCP tools or scheduled-task actions (AGENTS.md
  "Agents" rule).
- `GET /api/m3-plugins` (`list()`) starts sidecars as a side effect; `reload()` kills them all.
- Bypasses the Effect service model (plain classes, `node:*` built-ins, global `fetch`).

**Suitability as a module-isolation mechanism for optional AWS / messaging features (AWS-_,
BRK-_, MSG-\*).** **No.** Those features need server-side services with secrets-vault access,
orchestration events, MCP exposure, permission scopes and mobile/remote reach — exactly what the
plugin host does not provide — while its iframe/sidecar model adds an unsandboxed code-execution
surface. CMDeck's existing pattern is the better isolation boundary: optional workspace packages
(`packages/provider-*`, `packages/issue-tracker-*`, `packages/source-control-*`) providing Effect
layers registered by the server, gated by settings/disabled-by-default lists, with contracts in
`packages/contracts`. Recommend **"Not selected — do not introduce"** for the plugin host as a
module system. If third-party UI panels are ever wanted (would be a NEW-NN proposal needing
approval), the minimum bar is: a separate origin/port per plugin, `sandbox` without
`allow-same-origin`, a strict CSP, a scrubbed sidecar env, an allowlisted bridge mapped to
existing scoped RPCs, and an OS sandbox for sidecars (INF-09).
